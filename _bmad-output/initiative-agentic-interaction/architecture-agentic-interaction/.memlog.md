- (decision) Paradigm: ports and adapters. The agent is a driving adapter on the existing public API ports, exactly like the React frontend. Prevents: a second write path that bypasses service authz and domain rules.
- (decision) Agent runtime is a new deployable (agent-runtime), most downstream: calls the public API through the Spring gateway with a user token, never /internal, never the DB. No service calls the agent runtime except via an upstream-owned contract.
- (decision) Delegated token: CUMS mints a short-lived on-behalf-of JWT (own issuer, sub = user's cognito sub, act claim = agent run id) only for allowlisted users; every service accepts it through the shared-kernel multi-issuer decoder (precedent: Watch JWT, iss batbern-watch). Roles always from DB. In chat the organizer's own Cognito JWT is used.
- (decision) Inbound mail handoff: EMS (upstream, owner of inbound mail) calls agent-runtime through an EMS-owned /internal contract agent-inbound-mail, implementers in batbern.contracts config (ContractCalls). The agent mail address is a new alias handled by InboundEmailRouter.
- (decision) Outbound: the agent never sends mail itself; every mail goes through Mail Center operations as a tool call, so it lands in the outbound log and conversations.
- (decision) Tools: about 20 intent-level tools per role, each a composition of public API operations, defined in agent-runtime; risk class declared per tool (read, reversible-write, binding, audience). Raw 275 operations are not exposed.
- (decision) Autonomy gate (auto mode): read and reversible-write run autonomously; binding runs autonomously only above the confidence/precedent threshold else asks an organizer; audience always asks (#1179). Gate lives in agent-runtime, one place, before every write tool call.
- (decision) Precedent: the agent learns by retrieval from data the system already owns (60 events of history via read tools) plus the agent decision log of organizer approvals/denials. No fine-tuning, no separate vector store in the pilot.
- (decision) Agent decision log: agent-runtime owns its own tables (runs, steps, tool calls, gate verdicts, approvals) in the shared Postgres under its own schema prefix; every exchange is logged for evaluation; organizer can undo reversible actions from the log.
- (decision) Generated UI: agent emits a versioned JSON UI spec validated against a JSON Schema in docs/api; fixed catalog; one renderer in web-frontend, Tailwind-only so it works on public token-link pages; every action element references a tool call by name and goes through the gate.
- (decision) Card delivery: card stored server-side in agent-runtime; mail carries a signed token link; GET renders read-only, POST confirms (existing token/POST-only pattern).
- (decision) Cockpit: no new organizer CRUD screens during the initiative; organizer UI becomes an oversight console (activity feed, pending approvals, chat with generated views). Existing screens retire one by one when a generated view replaces them, owner go each.
- (decision) Pilot safety: allowlist and kill-switch are admin settings (AdminSettingsService keys agent.enabled, agent.allowlist); checked at token minting and in agent-runtime. Kill-switch off = agent-runtime answers nothing, mail alias falls back to forwarding to organizers.
