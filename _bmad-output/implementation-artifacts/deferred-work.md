## Cluster A — Auth/SSO hardening (REQUIRED before Apple/generic OIDC, Story 12.10)

These harden the federated-identity surface. Most are low-risk *while Google is the only IdP* (Google always asserts a verified email and the same `sub`), but become exploitable or noisy once a second IdP (Apple/generic OIDC) lands. **Treat this cluster as the precondition for Story 12.10.**

- **Primary-email federated linking has no `email_verified` gate** [`infrastructure/lib/lambda/triggers/pre-signup.ts:128-134`] — `pre-signup.ts` links a federated identity to a matching `user_profiles.email` WITHOUT checking the IdP's `email_verified` attribute (pre-existing Epic 12 behavior; the new verified-additional-email fallback IS gated). Low risk while Google is the only IdP (always verified); MUST be hardened before Apple/generic OIDC lands — an IdP asserting an arbitrary unverified email could link into a victim's account.
- **`AdminLinkProviderForUser` "already linked" not distinguished from real failures** [`pre-signup.ts:131-147, 212-219`] — a concurrent sign-in/retry throws `InvalidParameterException` and pollutes the `PreSignUpFailure` metric. `post-authentication.ts:105` already special-cases this; mirror that in `pre-signup.ts` for both linking paths. Two simultaneous first Google sign-ins for the same email both call link; the second throws already-linked, caught by the federated try/catch (no 503) but emits a misleading `PreSignUpFailure`. No idempotency guard. Low blast radius; revisit if the metric shows noise. [Edge]
- **Canonical-email restore lags one sign-in (`event.userName`-without-underscore fallback hardcodes provider `'Google'` + uses the whole userName as the subject)** [`pre-signup.ts:251-255, 268-270`] — real `PreSignUp_ExternalProvider` events are always `Google_<sub>` so the happy path is correct; the fallback is defensive-only and will mis-attribute the provider once Apple/another IdP lands (Phase 6). **Preferred fix: a PreTokenGen-restore variant** rather than relying on this PreSignUp fallback. Revisit when a second IdP is added. [Blind + Edge]
- **SES IAM grant includes `identity/*` wildcard** [`infrastructure/lib/stacks/partner-coordination-stack.ts:99-103` (origin of the pattern), `infrastructure/lib/stacks/company-management-stack.ts:182-186`] — both stacks carry a third resource ARN `identity/*` that negates the scoped domain ARNs. Tighten both stacks together after verifying which identity ARNs SES sends actually require (test in staging; sending uses From `noreply@batbern.ch` → `identity/batbern.ch` should suffice).
- **No cooldown/rate-limit on `POST /me/additional-emails/{email}/resend-verification`** [`services/company-user-management-service/.../controller/UserController.java:594`] — authenticated user can spam SES sends to their registered addresses. Add a per-row 60s cooldown (compare token issue time or a lightweight in-memory Caffeine cache) if abuse is observed.
- **`cognito-idp:ListUsers` granted but never called** [`infrastructure/lib/constructs/cognito-user-sync-triggers.ts` IAM grant; `infrastructure/lib/lambda/triggers/pre-signup.ts`] — spec-mandated (AC4 requires the grant; AC3 names it as a "MAY-use" destination-resolution fallback) but the handler resolves the destination solely from the DB row, so it is currently dead privilege, in mild tension with AC4's "least-privilege" framing. Implement the `ListUsers` fallback (would also address the anonymous-row + username==sub items) or drop the grant. [Edge + Auditor]
- **Destination correctness relies on the undocumented-in-AWS coupling "native Cognito username == sub"** [`pre-signup.ts:134-138`] — holds for this email-alias pool (Cognito-generated UUID usernames equal their sub) but admin-created/historically-imported rows could diverge, with no fallback (the granted `ListUsers` would be the natural one). Code matches the spec's literal instruction. [Auditor]
- **Turnstile fail-open-on-missing-token needs an explicit test + threat-model comment** (NEW — v1.1.0 release-PR bot review) — the Turnstile check fails open when no token is present; rate limiting is the compensating control. Add an explicit test asserting the fail-open behaviour and a threat-model comment documenting that rate limiting is the intended compensating control.
- **Verification-link replay-idempotency: documented as accepted design** (NEW — v1.1.0 release-PR bot review) — verification tokens are NOT single-use; replaying a verification link grants nothing additional. Accepted by design; capture the rationale as a code/threat-model comment so a future reviewer does not re-flag it.

## Cluster B — Cognito↔DB consistency / outbox

The recurring failure mode: a Cognito mutation succeeds, then the surrounding JPA transaction or an async step fails, leaving Cognito and Postgres divergent (orphan user, drifted username, locked-out speaker). The structural fix is an outbox / AFTER_COMMIT pattern (already spun out as Story 11.F.2 for the invitation path) plus a reconciliation job.

- **`runInvitedHook` performs Cognito mutation synchronously inside a JPA `@Transactional`** [`services/event-management-service/.../service/SpeakerWorkflowService.java:296-315`] — if any later step in the transaction throws (statusHistory write, eventPublisher listener), the DB rolls back but Cognito has already been mutated (password rotated, possibly never communicated). The AFTER_COMMIT TransactionalEventListener pattern is the right fix; code comment already flags the email-send variant but not the credential-issuance variant. [Blind #1 + Edge #9] — *NOTE: spun out as Story 11.F.2 per RD2 (2026-05-25); `SpeakerInvitedEvent` + `SpeakerAcceptedEvent` move Cognito mutation + email send to AFTER_COMMIT listeners. Tracked in sprint-status.yaml backlog.* — CONFIRMED still open 2026-06-07: `SpeakerWorkflowService.java:517,552` still carries the AFTER_COMMIT deferral comments; 11.F.2 has not landed.
- **AdminCreateUser succeeds → JPA commit fails on the same transaction → orphan Cognito user** [`services/company-user-management-service/.../UserService.java:710-747`] — Sequence: `createNewUser` (persists User) → `roleService.addRole` → `cognitoService.adminCreateUserSilently` SUCCEEDS → commit FAILS (deadlock, connection drop). Transaction rolls back; Cognito user remains. Next retry generates a different username; Cognito's `preferred_username` attribute now drifts from Postgres. Speaker logs in successfully via Cognito but `getCurrentUser` throws UserNotFoundException. Requires either an outbox pattern or a reconciliation job. [Edge #2]
- **AdminSetUserPassword succeeds → `@Async` email send throws → speaker locked out** [`services/event-management-service/.../SpeakerInvitationEmailService.java:113-117`] — Async failures are swallowed at the catch-all; the workflow transition still commits (speaker → INVITED). The new Cognito temp password is in nobody's hands. Operator must manually retry (the issue-invitation-credentials endpoint IS idempotent — but operators don't know it failed). Needs persistent retry queue or pre-send commit gate. [Edge #3]
- **`UsernameExistsException` swallow doesn't distinguish race from stale state** [`services/company-user-management-service/.../CognitoIntegrationServiceImpl.java:937-938`] — Swallowing INFO-logs as "idempotent no-op". If Cognito user is `ARCHIVED` (or otherwise unhealthy), the silent-swallow at provision time hides the problem; the issueInvitationCredentials call at INVITED then throws 422 — too late, the BATbern User row already exists. Detect at provision time via a follow-up `AdminGetUser` status check. [Blind #22]
- **Cognito `username` vs `preferred_username` drift on email change** [`services/company-user-management-service/.../CognitoIntegrationServiceImpl.java:920-932`] — `AdminCreateUser` uses email as the Cognito username; later calls use email again as the lookup key. If the speaker changes their email in CUMS post-provision, the Cognito record stays keyed by the old email → `getUserStatus(user.getEmail())` throws UserNotFoundException. Pre-existing Cognito-design pitfall. [Blind #16]
- **`UserReconciliationService.createMissingUser` `@Transactional` is a no-op (private + self-invoked)** [`services/company-user-management-service/.../service/UserReconciliationService.java:307-308`] — Spring AOP ignores `@Transactional` on private and self-invoked methods; the live tx is the outer `reconcileUsers()` (`:95`), so per-user `save()` (`:356`) flushes only at the batch commit → no per-user isolation. One over-length `pref_language` rolls back the entire nightly reconciliation batch and over-reports successes. Fix: make `createMissingUser` package-private + move to a separate bean (or use `TransactionTemplate`/`REQUIRES_NEW` per user) so each user commits independently. [Edge Case]
- **Throwaway temp password "discard" is theatrical + AWS SDK exception PII risk** [`services/company-user-management-service/.../UserService.java:1118-1124`] — `String throwawayTempPassword = null;` reassignment doesn't zero memory. More importantly, if `AdminCreateUser` fails with a validation error, some SDK error paths include the request body in serialized exception messages. `CognitoOperationException` wraps the cause and is logged. Needs an AWS SDK v2 exception-message audit to confirm passwords never appear. [Blind #3]
- **Plain-text temp password in service-to-service JSON; `RestTemplate` DEBUG logging risk** [`services/event-management-service/.../UserApiClientImpl.java:1782-1784`] — The response body contains the fresh temp password. Spring `RestTemplate` at DEBUG level dumps response bodies. Verify staging/prod log configs explicitly suppress this, or wrap the response in a redacting interceptor. [Blind #8]
