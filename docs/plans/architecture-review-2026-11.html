Sound context boundaries, one oversized context, and an API that has accreted

Verdict. The three contexts are cut correctly. CUMS owns identity, PCS owns partners, EMS owns the event. Behind the APIs, functionality is reused well in places, mail sending above all. Three things have drifted:

  • EMS has become the system: 74% of backend code, with no internal module boundaries.
  • The services call each other in both directions.
  • The OpenAPI surface has grown parallel endpoints for the same act: sending mail, uploading files, changing a task.

None of this is urgent. Most of it is cheap to fix now and expensive in a year.

Update, 7 Nov afternoon (develop @ 89b3618f). The figures below are from the morning snapshot. Re-measured after the rebase:

  • 342 operations (+13), and 100 EMS boundary violations.
  • One new near-duplicate: /newsletter/my-subscriptions next to /newsletter/my-subscription.

Two corrections:

  • The per-entity upload endpoints were allowed by an ADR-002 clarification. You decided to consolidate them anyway, and a new ADR-002 decision replaces that clarification.
  • All services share one database. EMS reads CUMS tables (user_profiles, companies) directly in SQL, and both services create logos. This is input for the database review.

Decisions are recorded in ADR-016 and the ADR-003 amendment.

1 · Who calls whom

Why it matters. A cycle means neither service can be deployed, tested or reasoned about alone. The fix is to name one direction as upstream, and it needs no message bus. Downstream services pull from upstream through /internal feeds polled by a ShedLock job, which the platform already has. That is boring, replayable and costs nothing extra.

  • CUMS → EMS. The merge call stays synchronous. EMS can block a merge and must return the preview counts, which an event can't do. Make the dependency a contract CUMS owns: /internal/user-references/preview|merge. Every service that stores usernames implements it, so CUMS doesn't know EMS by name. PCS stores usernames too and isn't covered by the merge today. The merge-request conversations flip direction: the Mail Center pulls open requests from CUMS.
  • EMS ↔ PCS. EMS is upstream, because partners consume events. The topic canvas gets partner topics from PCS in the frontend, not via EMS. Calendar RSVPs land in EMS's inbound mail. PCS pulls them from an /internal feed instead of EMS pushing them. PCS → EMS (event summary, attendance) remains, through /internal.

Checked: the EventBridge bus batbern-staging is still deployed with 0 rules. Five services (CUMS, PCS, EMS workflow and speaker workflow) still publish into it, and those events reach nobody.

2 · EMS is one context with ten sub-domains and no walls

Splitting EMS into more services would be the wrong move: every one of these modules reads the event. The right move is walls inside one deployable. Five packages already show the pattern works. Registration is the most tangled: 14 of its endpoints are hand-mapped inside EventController.

3 · Reuse behind the API: mail yes, uploads no

Reuse that did happen: attendee "topics from the floor" feed the same suggestion pool as partners. The Mail Center put every outbound mail in one log. Authorization lives in the services, with a guard test.

5 · UUIDs in paths: the rule and its exceptions

I agree with you. A sub-entity that exists only inside its parent has nothing a person would call it by, and an invented slug would be noise. There are three more cases where a UUID is the better choice, not just a tolerated one. I propose ADR-003 says this:

A meaningful ID is required for anything referenced from another service, stored in another service, or bookmarked and spoken by people: events, users, companies, sessions, topics.

A UUID is allowed when all three hold:

  • The thing has no natural name.
  • It never crosses a service boundary.
  • It sits in the path under its meaningful parent, and the service loads it scoped to that parent.

The scoping condition is the one that matters for security: without it, a valid UUID from another event can be edited or deleted through this event's path. I checked 5 of the 24 nested cases (photos, teaser images, materials, partner notes, thank-you notes) and all 5 scope correctly. Materials check the session slug, which has a unique constraint (V4). A shared findByIdAnd{Parent} convention plus one test per nested resource would make this a rule rather than a habit.

6 · EMS module map and where it is violated today

Two cuts differ from section 2. Both came out of the measurement:

  • Mail splits in two. Mail core is the pipeline every domain uses: rendering, variables, sending, delivery status. Mail center composes, forwards and runs conversations, and is allowed to read the domains.
  • Agenda planning and publishing move above speakers. They are the only places that join sessions with the speaker pool. Without this split, sessions and speakers would depend on each other through 17 references.

Enforcement. One ArchUnit test using layeredArchitecture() over the module packages, with the 101 current references frozen as known violations (FreezingArchRule). New violations fail the build from day one, and the frozen list can only shrink. This needs the classes moved into module packages first. The cheaper first step is a test over the five packages that are already vertical.

Method: each of the 489 EMS classes was assigned to a module by name and package (rules in scripts/architecture/ems-module-deps.py on the review branch). A reference is any EMS class name appearing in another class's code, comments excluded. About 30 classes were assigned by hand. The counts depend on these assignments, so treat them as a map, not a census.

7 · Recommendations, in order

  1. Delete dead surface. Two specs, six orphan endpoints, the dead fetchPreview hook. Low effort. Removes about 25 ops. Stopping the speaker-coordination ECS task and removing the subscriber-less EventBridge bus and its publishers are production changes, so they are your decision.
  2. Add a contract guard for frontend paths. Fail the build when a frontend service calls a path the spec doesn't have. This would have caught GET /publish/{phase}/preview, which exists in neither the spec nor the backend. Low effort. Stops the drift from coming back.
  3. Finish 16.8c. Fold newsletter, notice, venue and slides sends into the Mail Center endpoint. Already planned and gated on your go.
  4. Break the cycles. Service-to-service calls go through /internal only. Move the four machine-only endpoints out of the public spec. Downstream pulls feeds, and the merge becomes a CUMS-owned contract (section 1). Medium effort. No new infrastructure.
  5. One upload contract. /uploads/{purpose} in every service, with mechanics in shared-kernel and one handler per purpose. Migrate one purpose per story. Medium effort. 11 operations become 3; decided 7 Nov.
  6. Wall EMS from the inside along the module map in section 6. Freeze the 101 current violations in ArchUnit, then work down the hotspots, starting with EventController and GlobalExceptionHandler. Incremental, never a big bang.
  7. Settle the conventions. Amend ADR-003 with the rule from section 5, nest the one stray AI endpoint, pick one speaker key, use one PATCH for tasks, one settings resource. Decide once, apply when touching each area.
  8. Follow-up reviews of what this one left out: frontend architecture, database schema, gateway, Watch API. Logged in the action list. One review per area.

For the agents themselves, three changes:

  • One short map, loaded everywhere. At most 4 KB: modules, directions, reuse catalog, API rules. It goes in project-context.md, which every BMAD workflow loads, and a pointer goes in CLAUDE.md for sessions without BMAD, like the parallel issue work. Amelia already loads about 80 KB on every activation, so the map should replace something rather than add to it.
  • A design check before coding. The story carries a five-line architecture note: modules touched, new dependencies, new endpoints with the nearest existing one considered, components reused. Create-story drafts the note and dev-story confirms it before the first test. The thinking happens while it is still cheap to change course.
  • An architecture reviewer in code review. One more layer in bmad-code-review reads only the diff and the map, with fresh context. A reviewer that didn't write the code finds what the author rationalized.
