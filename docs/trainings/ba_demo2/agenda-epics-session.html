Step 2: Design Epic List

Grouping requirements into user-value epics

Agent Response (John) — Epic Design Principles

Designing the epic structure.

Principles I follow for epic design:

  • User-value first — each epic delivers a coherent user outcome, not a technical layer
  • No forward dependencies — stories within an epic only depend on earlier stories
  • Independently demoable — each epic can be demonstrated to stakeholders
  • Right-sized — neither too large (unclear progress) nor too small (overhead)

I identified 6 user value themes from the requirements. Proposed epic structure:

Story 8.1.1: Create Partner Meeting with Basic Details

Given the agenda has items

Key Takeaways

What BAs and PMs should learn from this session

User-Value Epics, Not Technical Layers

John proposed epics organized by user outcome (meeting creation, live meeting, minutes, post-meeting), not by technical layer (backend, frontend, database). Each epic is independently demoable to stakeholders.

Domain Expertise Improves Structure

The user's 3 adjustments transformed 6 epics into a tighter 4-epic structure. Merging voting into presenter mode and distributing action items across epics was better than what the agent proposed. The human steers, the agent executes.

Collaborative Facilitation Catches Gaps

Auto-generation would have missed the custom agenda item gap in Story 8.3.1. The user's domain knowledge caught it. One missing acceptance criterion could have led to incomplete meeting minutes in production.

Cross-Cutting Concerns Belong in Context

Action items (FR9) were originally a standalone epic. Distributing them across the epics where they're used (creation in 8.2, review in 8.3, carry-forward in 8.1) makes each story demoable and avoids isolated features.

Systematic Validation Prevents Drift

The 5-point validation is not a checkbox exercise. It verified FR coverage (35/35), architecture compliance, story quality, epic structure, and dependency chains. Running this before implementation prevents discovering gaps mid-sprint.

Minimal Input, Maximum Output

The user's inputs were brief: one command (ce), three adjustments, one bug catch, and four confirmations (c). The PM agent drove the analysis, extraction, and writing. BAs should focus on reviewing and redirecting, not generating content.
