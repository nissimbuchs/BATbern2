Phase 1 — Brainstorm: Partner Features

Exploring current state and generating enhancement ideas

User Prompt (voice input)
"I want to brainstorm with you about the partner management features. Please look at the current partner management for the partner himself and for organizers. Then come up with some ideas how we could enhance the functionality for partner management."
What Happens Internally
Mary uses the Explore sub-agent to do a very thorough codebase analysis — reading controllers, services, domain models, DTOs, frontend components, user stories (Epic 8), and OpenAPI specs. This grounds the brainstorm in actual code, not assumptions.
Mary — Current State Analysis + Enhancement Ideas
Current State: BATbern has a two-sided partner platform. Partners can view attendance analytics, vote/suggest topics, and receive calendar invites. Organizers can manage the full partnership lifecycle, create meetings, write internal notes, and view RSVPs.

Key observation: Partners are mostly passive recipients. They receive invites, see data, vote on topics — but have almost no ability to initiate, communicate, or self-serve.

Enhancement themes proposed:
  • 🟢 Theme 1: Partner Self-Service Empowerment (contact mgmt, RSVP visibility, meeting requests, document vault)
  • 🔵 Theme 2: Richer Analytics & Insights (YoY trends, benchmarking, PDF report)
  • 🟡 Theme 3: Smarter Meeting Coordination (agenda collaboration, reminders, post-meeting notes sharing)
  • 🟠 Theme 4: Lifecycle & Relationship Management (renewal alerts, tier workflow, onboarding checklist)
  • 🔴 Theme 5: Communication & Engagement (messaging, topic threads, notification center)

Top 5 picks by value/effort: RSVP visibility, renewal alerts, notes sharing, YoY indicators, PDF report
User Response — Narrowing Scope
"Ok. I like the RSVP visibility, the note and meeting minutes and attachments sharing. On analytics, we already have a top-level analytics page that organizers and partners can see with all you proposed. Remember them. But I also had another idea — I thought we could add functionality for the yearly invoice management. Can you help me brainstorm on this?"
Training Point: Memory + Pivot
Notice two things: (1) The user corrects a wrong assumption (analytics already exists) — good analysts welcome corrections; (2) The user pivots to a new idea mid-brainstorm. Mary saves the selected features to persistent memory before pivoting, ensuring nothing is lost.

Phase 1 — Brainstorm: Invoice Management

Deep-diving a new capability idea through structured Q&A

Mary — Invoice Brainstorm (Themes A–D)
Foundation already exists: partnershipCost field on Partner entity — the financial seed is there.

Key questions before brainstorming:
  • Who generates the invoice — BATbern platform or external tool (Bexio)?
  • What's the billing cycle — annual, per-event, or both?
  • Swiss QR invoice (QR-Rechnung) required, or simple PDF?
  • Who sees invoices — organizer only, or partner too?

Themes proposed: A) Invoice Tracking (lightweight), B) PDF Generation, C) Payment Integration (advanced), D) Financial Overview
User — Answering the Key Questions
"1: A simple PDF invoice is enough.
2: No, we create them by hand. You could add functionality to create the invoice. The partner has a self-service tab to edit the invoice information (contact, address, order number if exists). Then you have all info to create the invoice.
3: Pure annual fee. Would be great to have a small table for organizers to set the fee easily for each partner.
Let's focus on core, make it shine, nice to have. Allow also for sending reminder mail on overdue invoices manually."
Training Point: Structured Elicitation
Mary asked 4 scoping questions before proposing solutions. This is the analyst's core skill: resist the urge to dive into solutions until you understand the constraints. The user's answers eliminated Swiss QR, Bexio integration, and complex payment flows in one exchange — saving hours of unnecessary design work.
Mary — Crystallized Invoice Spec
New entities proposed:
• PartnerInvoice — id, companyName, invoiceNumber (BAT-2026-ACME-001), billingYear, amount, dueDate, status (DRAFT→SENT→PAID→OVERDUE→CANCELLED), paidAt, reminderSentAt
• PartnerBillingInfo — companyName (PK), billingContactName, billingContactEmail, billingAddress, vatNumber, purchaseOrderNumber

Organizer fee table: Inline-editable table (Partner | Tier | Annual Fee | Invoice Status) with year switcher + "Create All Drafts" bulk action

Invoice lifecycle: DRAFT → [Send] → SENT → [Mark Paid] → PAID / OVERDUE → [Send Reminder] → [Mark Paid]

Partner self-service: Billing Info tab in portal (form + invoice history + PDF download)
User — Final Confirmations
"1: configurable in the admin section [for the association address]
2: that works [invoice number format BAT-2026-ACME-001]"
Memory Written — Invoice Spec
File: memory/project_invoice_management_spec.md

Full data model, lifecycle, organizer fee table, PDF template layout, partner self-service tab, email flows, and overdue reminder (manual trigger) all documented and saved to persistent memory.

Phase 2 — PRD Creation Workflow

12-step structured facilitation from vision to complete requirements document

User Prompt
/bmad-bmm-create-prd
What Happens Internally
The workflow loads _bmad/bmm/workflows/2-plan-workflows/create-prd/workflow-create-prd.md, then follows a step-file architecture: each step is a separate file loaded one at a time (just-in-time). The agent never reads ahead. Each step updates the PRD frontmatter (stepsCompleted) before loading the next step. This ensures no steps are skipped and state is always recoverable.

Key Training Takeaways

What this session demonstrates about effective BMAD analyst collaboration

🎯 Ground in the Codebase First

Before brainstorming enhancements, Mary read the actual code. Enhancement ideas that contradict existing architecture get caught immediately, not during development.

❓ Questions Before Solutions

When invoice management was proposed, Mary asked 4 scoping questions before generating a single feature idea. This eliminated Swiss QR, Bexio, and payment integrations in one exchange.

🧭 Use /bmad-help to Navigate

After brainstorming, the user didn't know what came next. /bmad-help read the completed work and pointed to the required next step (PRD) instead of an optional one (brief).

✏️ Review Before C — Always

The architect PDF note and the i18n NFRs were both added by the user before pressing C. Pressing C without reviewing is how requirements get lost. Read before you continue.

💾 Memory Preserves Context

When the user pivoted from features to invoice management, Mary saved the selected features to memory first. Nothing was lost across the topic shift or across future sessions.

📋 FRs Are the Contract

Step 9 produces the binding capability contract. The agent emphasized: "Any feature not listed here will not exist in the final product." This forces completeness before architecture begins.

⏭ Skip Optional Steps Confidently

Domain requirements (step 5) and innovation analysis (step 6) were skipped because the agent assessed they didn't apply. Skipping adds speed; the agent explains its reasoning transparently.

🔄 Fresh Context for Each Phase

The PRD workflow ran in the same session here (training demo). In production: run each major workflow in a fresh context window to avoid token pressure and context drift.

WHAT COMES NEXT IN A FULL BMAD SESSION (Phases 3+)
