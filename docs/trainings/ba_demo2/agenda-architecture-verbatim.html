Category 1: Data Architecture

Decision 1.1: Entity Model Structure

Key design choices:

  • meetingCode as meaningful ID (ADR-003) — pattern: PM-{year}-{Spring|Autumn} (e.g., PM-2026-Spring)
  • Minutes content stored as JSONB — structured sections (attendance, votes, notes per item, documents) rather than flat text. Allows auto-assembly from item contributions and structured rendering.
  • Action item sourceItemId for carry-forward chain — self-referencing FK to track origin across meetings
  • All cross-service references use meaningful IDs (companyName, ownerUsername) per ADR-003

Does this entity model look right to you? Any entities to add, merge, or rename?

Category 2: Authentication & Security

Decision 2.1: Presenter Mode Authorization

No new auth mechanism needed — standard JWT role check. But we need a rule:

  • Organizer role required for: create/edit meeting, start Presenter Mode, cast votes, publish minutes
  • Partner role required for: view published minutes, RSVP, fee acceptance, feedback pulse
  • Public: None — all endpoints are authenticated

One nuance: Should Presenter Mode have a "lock" so only one organizer can be in Presenter Mode for a given meeting at a time? Given the single-operator model, I'd suggest a simple presenterSessionStartedBy field on the meeting entity — not a distributed lock, just a soft indicator. If another organizer tries to start, they see "Meeting is being presented by [name]."

Your thoughts on the presenter lock approach?

Category 3: API & Communication

Decision 3.1: Minutes Auto-Assembly Pattern

This is the most architecturally significant decision. Two approaches:

Option A — Backend Assembly: Each agenda item interaction (attendance toggle, vote cast, note save) calls its own endpoint. The backend MeetingMinutesService assembles the minutes by querying all related entities when the organizer clicks "Review Minutes."

  • Pro: Simple API design, no special pattern needed, minutes always fresh from source data
  • Pro: Each endpoint is straightforward CRUD
  • Con: Minutes review requires multiple DB queries to assemble

Option B — Event-Sourced Contribution: Each interaction writes a "minutes contribution" record. Minutes are assembled by replaying contributions in order.

  • Pro: Audit trail of every contribution
  • Con: Over-engineered for bi-annual usage with single operator, adds complexity

My lean: Option A — Query-based assembly. The entities already hold all the data (attendance, votes, documents, notes). The minutes service simply queries and structures them. No new pattern needed — just a well-designed query.

Do you agree with Option A, or do you see value in the event-sourced approach?

Decision 3.2: Auto-Save API Pattern

For Presenter Mode auto-save (< 2s):

  • Frontend: Debounced useMutation (TanStack Query) — saves 2 seconds after last keystroke
  • Backend: PATCH /api/v1/partner-meetings/{meetingCode}/agenda-items/{itemId}/notes — partial update endpoint
  • Optimistic UI: Show "Saved ✓" immediately, roll back on error

This follows the standard TanStack Query mutation pattern already used elsewhere in the app. No new infrastructure.

Category 4: Frontend Architecture

Decision 4.1: Presenter Mode Layout Strategy

Two options for the three-zone Presenter Mode layout:

Option A — Dedicated PresenterLayout component: A new top-level layout (like OrganizerLayout) that renders at /partner/meetings/{code}/present. Full-screen, no nav bar, dark theme forced.

Option B — Modal/overlay on existing layout: Presenter Mode as a full-screen overlay on the existing partner meeting page.

My lean: Option A — Clean separation. Presenter Mode has fundamentally different layout requirements (no nav, fixed zones, keyboard shortcuts, projector-optimized). A dedicated layout component is cleaner than fighting the existing layout.

Category 5: Infrastructure & Deployment

Decision 5.1: Scheduled Workflows (Fee Reminders, Feedback Pulse)

The PRD requires scheduled triggers: fee reminders at 7/14 days, feedback pulse 24h after publish. Options:

Option A — Spring @Scheduled in partner-coordination-service: Simple cron jobs that query for pending items and send emails. Already running in the same service.

Option B — AWS EventBridge / Step Functions: External scheduling for better observability.

Training Note — Minutes-as-Byproduct Pattern

The minutes-as-byproduct decision is the core architectural innovation. Winston evaluated two approaches:

  • Option A (Query-Based Assembly): Each action saves to its own entity. Minutes are assembled on-demand by querying all related data. Simple, no new patterns.
  • Option B (Event-Sourced): Each action emits a domain event. Minutes replay the event stream. More elegant but adds significant complexity.

Winston chose Option A because: the data is always authoritative (no stale projections), bi-annual usage does not justify event sourcing overhead, and it follows the existing CRUD patterns. This is a textbook example of choosing the simpler architecture when the usage pattern does not demand complexity.
