Training Note — Why Brownfield Matters

Winston correctly identified this as brownfield — an important distinction. Key decisions: meetingCode as meaningful public identifier (pattern: PM-{YYYY}-{Spring|Autumn}). Minutes content as JSONB for auto-assembly. Action item carry-forward via self-referencing sourceItemId FK. All cross-service references use meaningful IDs per ADR-003.

2. Authentication & Security

  • Organizer role: create/edit meetings, Presenter Mode, voting, minutes publishing
  • Partner role: RSVP, view published minutes, fee acceptance, feedback
  • Presenter Mode soft lock: presenterSessionStartedBy + presenterSessionStartedAt fields — informational only, not a distributed lock

3. API & Communication — Minutes Auto-Assembly

Query-Based Assembly (Option A) chosen over event-sourced approach:

  • Each organizer action persists to its own entity (attendance, votes, documents, notes)
  • MeetingMinutesService.assembleMinutes(meetingCode) queries all entities and structures them into JSONB
  • Assembled on-demand when organizer clicks "Review Minutes" — always reflects current state
  • After publish, JSONB content becomes the immutable record

Rationale: Simple, no new patterns, bi-annual usage doesn't justify event sourcing complexity.

Auto-Save Pattern: Debounced useMutation via TanStack Query — fires 2 seconds after last input. Backend: PATCH endpoint. Optimistic UI with "Saved" indicator.

3 API Endpoint Groups:

  1. Meeting management — CRUD + status transitions + agenda configuration
  2. Presenter Mode — attendance, voting, notes, documents, snapshots
  3. Post-meeting — minutes review/publish, fee acceptance, feedback pulse

4. Frontend Architecture — Dedicated PresenterLayout

New top-level layout (not a modal or overlay) with three fixed zones:

5. Infrastructure — No New Services Required

  • Spring @Scheduled for fee reminders (7/14 day) and feedback pulse (24h) — not EventBridge
  • No new ECS services, databases, WebSocket, or CDN configuration
  • Extends existing partner-coordination-service Fargate task

Implementation Sequence: Schema → OpenAPI → Backend CRUD → Presenter Layout → Agenda Items → Minutes → Post-Meeting → Action Items

Training Note — Minutes-as-Byproduct Pattern

The minutes-as-byproduct decision is the core architectural innovation. Winston evaluated two approaches:

  • Option A (Query-Based Assembly): Each action saves to its own entity. Minutes are assembled on-demand by querying all related data. Simple, no new patterns.
  • Option B (Event-Sourced): Each action emits a domain event. Minutes replay the event stream. More elegant but adds significant complexity.

Winston chose Option A because: the data is always authoritative (no stale projections), bi-annual usage does not justify event sourcing overhead, and it follows the existing CRUD patterns. This is a textbook example of choosing the simpler architecture when the usage pattern does not demand complexity.

Auto-Save Hook Pattern (TypeScript) 
const useAutoSave = (mutationFn: MutationFunction, delayMs = 2000) => {
  const mutation = useMutation({ mutationFn });
  const debouncedSave = useMemo(
    () => debounce((data) => mutation.mutate(data), delayMs),
    [mutation, delayMs]
  );
  return { save: debouncedSave, status: mutation.status };
};

Communication Patterns:

  • Meeting status transitions: DRAFT → SCHEDULED → IN_PROGRESS → COMPLETED (no backward transitions)
  • 5 email notification template identifiers defined: partner_meeting_invite, partner_meeting_minutes, partner_meeting_fee_request, partner_meeting_fee_reminder, partner_meeting_feedback_pulse

Process Patterns:

  • Presenter Mode entry/exit sequences — 5-step entry, normal exit to minutes review, escape exit with resume
  • Minutes assembly sequence — query attendance, iterate items, merge into JSONB
  • Action item carry-forward logic — copy open items, set sourceItemId, calculate carryForwardCount, flag urgency at 2+

7 Enforcement Guidelines:

  1. Follow the table naming prefix partner_meeting_* for all new tables
  2. Use the exact JSONB structure for minutes content — no variations
  3. Use the useAutoSave hook for all auto-save — no custom implementations
  4. Follow the Presenter Mode entry/exit sequence exactly — no shortcuts
  5. Use meaningful IDs in all API URLs and responses — never expose UUIDs
  6. Store enums as lowercase_snake_case in DB, UPPER_CASE in JSON/API
  7. Place all Presenter Mode components under src/components/presenter/

Training Note — Why Enforcement Guidelines Matter

The 7 enforcement guidelines and 8 anti-patterns are the most operationally important part of the architecture document. In an AI-assisted development workflow, multiple agents (or the same agent across sessions) will implement different stories from this architecture.

Without these explicit rules, common divergences include: one agent using WebSocket for auto-save while another uses HTTP PATCH, one storing partner names directly while another follows ADR-004, one placing Presenter components in organizer/ while another uses presenter/.

The enforcement guidelines act as a contract between the architect and every implementing agent. They eliminate ambiguity at the exact points where AI agents are most likely to make inconsistent choices. This is unique to AI-assisted architecture — human teams use code reviews to catch drift; AI agents need the rules upfront.

Training Note — How Validation Catches Gaps

The validation step is not ceremonial. Winston systematically checks three dimensions:

  1. Coherence — do the decisions contradict each other? (e.g., choosing WebSocket but then saying no new infrastructure)
  2. Coverage — is every functional requirement traceable to a specific entity, component, and API endpoint?
  3. Readiness — is there enough detail for an AI agent to implement without making assumptions?

In this case, validation found zero critical gaps and only 3 important items (library selections) that can be resolved during implementation. This is the green light for creating epics and stories. Without validation, missing gaps would surface as blockers during implementation, causing rework.

Key Takeaways

What BAs and architects should learn from this session

Brownfield Efficiency

For brownfield projects, the architecture session skips template evaluation entirely and focuses on the genuinely new elements. Winston identified only 4 new patterns needed atop a mature, production-proven stack. This prevents over-engineering.

Decisions Over Description

The architecture document is not a restatement of requirements. It is a set of decisions with rationale. "Query-based assembly, not event sourcing, because bi-annual usage does not justify the complexity" — this is the kind of reasoning that prevents future debates.

Patterns for AI Consistency

The 7 enforcement guidelines and 8 anti-patterns are unique to AI-assisted development. Human teams rely on code reviews and tribal knowledge. AI agents need explicit, upfront rules to avoid drift across independent implementation sessions.

Validation Before Implementation

Winston's systematic validation caught that all 10 FR groups are covered, all NFRs addressed, and no critical gaps exist. Running validation before creating stories prevents discovering architectural holes mid-sprint.

Minimal User Input Required

The user's inputs were remarkably brief: CA docs/.../prd.md, a document confirmation, and then C seven times. The architect agent drove the entire analysis. BAs should focus on reviewing and redirecting, not generating content.

Traceability Chain

The session established a clear traceability chain: Brainstorm (35 ideas) → UX Spec (5 journeys) → PRD (10 FR groups) → Architecture (11 entities, 30+ patterns). Every decision traces back to a requirement, which traces back to a user need.
